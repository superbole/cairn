# Decisions

Why this project is the way it is: one row per decision that has been **answered**, naming the
option that was rejected and what it cost. Open questions live in `NEXT.md`'s `## Decisions`
list — the two are opposite ends of the same thing, never the same file.

Rule-level incidents (why a specific line in a `SKILL.md` or the rules payload exists) are
recorded separately, in `plugins/cairn/skills/{next,wrap}/references/incidents.md`. This file
is for project-level decisions those records have no home for.

## D1 — what the split actually is

Verified 2026-09-05 against the source, because the question "does an install need the private
side?" had never been answered from the code:

**An install needs only `.claude-plugin/marketplace.json` and `plugins/cairn/`.** Nothing else in
this repo is load-bearing at runtime. `session_orientation.py` resolves the project root as
`$CLAUDE_PROJECT_DIR` → walk up for a `NEXT.md` → `cwd`, so it reads whatever project the session
is in. This repo's `NEXT.md`, `BACKLOG.md`, `CHANGELOG.md`, `briefs/` and `INBOX.md` are its own
dogfooding, indistinguishable in kind from any other project's copies.

| Public | Private |
|---|---|
| `plugins/cairn/` — hooks, rules, skills, tools | `briefs/` — most name work projects or internal servers |
| `.claude-plugin/marketplace.json` | `docs/review/` — per-lane dossiers |
| `README.md`, rewritten for a stranger | `INBOX.md` |
| `docs/guide.md`, `design-notes.md`, `file-formats.md`, `running-a-batch.md`, this file | this repo's git history, kept as the record |
| `skills/*/references/incidents.md`, hostnames genericised | |
| `NEXT.md` / `BACKLOG.md` / `CHANGELOG.md` — **started fresh**, items migrated only after triage | the current three, which name work servers and client projects |

**The incident records go public.** They are not needed to run the plugin, but they are the reason
an agent does not reason past a rule — `CLAUDE.md` requires reading them before weakening one.
Developing from a public clone that lacks them loses that guardrail, and publishing rules without
them gives a stranger no reason to trust the rules' shape. Genericise the hostnames only
(`git2.example-corp.net`, as `test_issue_host.py` already does) and keep the measurements: the
measurement is the evidence, the host is not.

**Ordering.** B12 (de-personalise the payload) must land before the public repo is seeded — the
payload installs into every user's `~/.claude/CLAUDE.md`, and today it opens by naming one person's
medical history. B51 (the disclosure review) is the seeding step itself.


## Design note — name the HORIZON a guard compares against, 2026-09-06

Not a decision with a rejected option, but the generalisation of two separate incidents on
2026-09-05, kept here because it is the kind of thing that cannot be re-derived from the code.

**Twice in one day, a guard was correct in mechanism and wrong in horizon:**

| Guard | Compared against | Should have compared against | Cost |
|---|---|---|---|
| `wrap/SKILL.md`'s *"re-read `NEXT.md` from disk first"* | the file on **this disk** vs the copy in context — a stale CONTEXT | what the other session had, which lives on **`origin`** — a stale CHECKOUT | Four id collisions in one day (B75). The rule was followed exactly and did not help: the other session's numbers were never on this disk to be re-read. |
| `atlas`'s predeploy staleness check | the branch vs **`origin/<branch>`** | what **production is actually running** | A feature branch 4 commits behind `origin/main` passed the guard clean and reverted production for 5h34m. |

**The pattern:** a guard that reads a real signal, reports honestly, and answers a question
adjacent to the one that matters. It cannot be caught by testing the guard — the guard works. It is
caught only by asking *what could actually hurt me here, and is that the thing being measured?*

**So: whenever a check is added to this plugin, state its horizon in the code, next to the check.**
B86 does this deliberately — an ahead-count against `origin/<branch>` is right there because the
question is literally *did anything leave this machine*. B80 states the opposite limit as plainly:
consulting `origin` at allocation time cannot catch two sessions that have both not pushed yet, and
that is why B79 is the floor rather than B80.

**This is also why B79 outranks B80** despite being a detector rather than a preventer. B79's
horizon is *one disk, right now*, which is the only horizon guaranteed to contain both sides of a
collision once the branches meet. Ranking them the other way round was a live risk on 2026-09-05
and was corrected before it reached the queue.
