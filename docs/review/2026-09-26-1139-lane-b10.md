# Lane B10: no baseline reads `CAIRN UNKNOWN`, not confident `[SKIP]` / `OPEN`

Backlog item **B10: "With NO baseline at all, the receipt reports a confident `[SKIP]` instead of
'cannot tell'"**, brief `briefs/receipt-no-baseline.md`. One commit on the lane branch, not pushed.
Owned files only: `plugins/cairn/hooks/wrap_receipt.py`, `plugins/cairn/tools/test_wrap_receipt.py`,
`plugins/cairn/tools/test_archive_guard.py`. The last one changed by one assertion, in section 4,
which the brief said it would.

## 1. What changed and why

### Re-checked against HEAD (v1.63.0) first, as the brief asked

I reproduced the bug with fixtures before changing anything (a scratch script, temp config dir,
five scenarios). **The defect exactly as the entry describes it no longer reproduces.** At HEAD,
`_changed()` returns `None` with no baseline, and `_changed_by_session()` returns that `None` before
it ever looks at `paths`. `attribution()` only builds `paths` once a reflog window exists, so
`paths: [], commits: None` can't happen any more. With a truly missing baseline, `next_rewrite`,
`changelog` and `commit` already read `[ ? ]`, and never `byte-identical`. Scenario A below (the
filed `--resume` shape, complete wrap) already read `CAIRN UNKNOWN` at HEAD.

**Two holes from the same family were still there at HEAD:**

- **With no baseline, a stale `.last_wrap` on its own read `CAIRN OPEN`.** An INBOX bullet or a
  dangling brief link did the same. The printed note right above the token said *"Hence UNKNOWN
  rather than OPEN"*, so the receipt contradicted itself. Scenario C (a session that did nothing,
  where an earlier session left an unwrapped commit) read `OPEN`. That is exactly the cry-wolf
  that D36 says `archive_guard.py` refuses to act on.
- **A baseline file that loads but holds no snapshot counted as a baseline.** `have_base =
  bool(base)` was true for a dict with no `files` map. `_changed()` then treated every tracked file
  as changed, a comparison that was never made. Scenario D read **`CAIRN SET`**. Scenario E (idle)
  printed `[SKIP] NEXT.md changed since session start, but the change arrived by a change from
  outside this session` about a file nobody touched. That is B10's pattern exactly: a positive
  claim about a comparison that never happened.

### The fix, mapped to the entry's three parts

1. **`_changed_by_session` returns `None` when attribution can see nothing.** This was already true
   at HEAD, so the change is an explicit `_usable(base) is None -> None` guard. The guarantee now
   holds by construction rather than by the order of two calls. Related hardening in `_changed()`:
   a file the snapshot doesn't *mention* now returns `None` (unmeasured). It no longer shares
   `.get() -> None` with "absent at session start", which would have credited it as created this
   session.
2. **The measuring branch is gated on a baseline that actually loaded.** New `_usable(base)`
   requires a dict with a `files` dict and a positive numeric `at`. `head` may be `""`, because
   attribution already reads that as blind. It's applied at every entry point that takes a baseline
   (`steps`, `verdict`, `attribution`, `_nothing_to_wrap`, `work_head`, `record`, `--check`).
   `baseline()` itself still returns the raw file, so `--stamp-baseline` can still say it REPLACED
   one.
3. **With no usable baseline the verdict is `UNKNOWN`, and the receipt says so once, at the top.**
   `verdict()` now tests `_usable(base) is None` **first** and returns only `UNKNOWN`. The reasons
   start with `NO_BASELINE_REASON`, followed by any baseline-independent gaps (marker, inbox,
   briefs), each marked *"(current state; with no baseline this cannot be attributed to this
   session)"*. The gaps still show in the reasons; they just can't decide the verdict.
   - The printer states the missing baseline once, in the top NOTE. Each blind row reads just
     `not measured: no session-start baseline`. The `attribution UNAVAILABLE` line and the
     `! NO_BASELINE_REASON` line would repeat the same fact, so they aren't printed.
   - The NOTE now names the third cause. Before, it said only "started somewhere else"; now it
     says *"Either this session started somewhere else, or SessionStart never ran for it here (a
     --resume or a crash-restart)."* The resume cause is the one B10 was filed on.
   - The marker step without a baseline no longer claims `.last_wrap == HEAD ..., stamped this
     session`. That is a claim about *when*, and `base_at` is the only clock available. A matching
     marker now reads `unverifiable`. A missing or stale marker still reads `skipped`, because that
     comparison really was made.
   - `orientation_line()` for a stored `UNKNOWN` reads the cause off the receipt's own `baseline`
     field. Before, it always said "from where it was started", which is wrong for a resume.
   - The `attribution_reason` string for no baseline was `"no session baseline (a bare CLI run
     outside a session has none)"`, which asserted one of three causes. It is now `"no
     session-start baseline"`. This string is signed into the receipt id, so ids differ for the
     same tree. No receipt is compared across versions, so nothing breaks.

Also: section 11c of `test_wrap_receipt.py` asserted the behaviour this fix removes: with no
baseline, an un-drained inbox read `OPEN`. It is rewritten. The ordering guarantee (`skipped`
outranks `unverifiable`) is now pinned *with a baseline* (baseline stamped, reflog removed, inbox
not drained -> `OPEN`). A new 11c-bis pins the no-baseline case as `UNKNOWN` with the inbox gap
visible in the reasons.

New test section 12 (B10):

- **12a.** The `--resume` fixture from the brief: no stamp, real edits to `NEXT.md` (37 lines) and
  `CHANGELOG.md` (79 lines), a commit, and a marker that was not re-stamped. It reads `UNKNOWN`.
  No step detail claims a snapshot comparison. The CLI `--record` prints the NOTE exactly once and
  before the table, never `[SKIP] next_rewrite`, `[SKIP] changelog` or `CAIRN OPEN`. It names
  `--resume` and still prints `! marker:`. The receipt records `baseline: false`, and the
  orientation line names the cause.
- **12b.** A complete resume-shaped wrap: the marker is `unverifiable`, not `ran`.
- **12c.** D36's shape (idle session, inherited stale marker, no baseline) reads `UNKNOWN`.
- **12d.** A hollow baseline (no `files`, or no `at`) is not usable and reads `UNKNOWN`. It read
  `SET` at HEAD. The idle variant makes no "since session start" claim.
- **12e.** A snapshot missing one tracked key reads `None` for that file and still measures the
  others.
- **12f.** A **genuine idle session with a real baseline still reads `[SKIP]` "byte-identical"**
  and `OPEN`. The fix is not a blanket `UNKNOWN`.
- **12g.** The property check: `verdict()` with base `None`, `{}`, hollow, or no-`at`, and every
  REQUIRED step forged `ran`, still returns `UNKNOWN`.

## 3. Decided on the user's behalf

- **Any no-baseline session reads `UNKNOWN`, not just blind-but-not-skipped ones.** The brief's
  part 3 says "the verdict is `CAIRN UNKNOWN`". I applied that to every no-baseline session, which
  **reverses one B2 guarantee in that case**: *"a wrap that is both incomplete AND blind still reads
  `OPEN`"* no longer holds when the blindness is a missing baseline. It still holds when a baseline
  exists and the reflog is blind (test 11c).
  - **Reason:** `OPEN` asserts a wrap was *owed*, and only a baseline can measure that
    (`_nothing_to_wrap`). Without one, a forgotten marker and an inherited one look the same. The
    guard already decided this in D36.
  - **Cost:** a resumed session that really did forget to drain INBOX or re-stamp the marker gets
    `UNKNOWN`, not `OPEN`. The gap still shows in the reasons, prefixed `!`.
  - **If you disagree:** the narrow alternative is to keep `OPEN` for inbox and briefs and only
    exempt the marker. I rejected it because the capture process adds INBOX bullets to idle
    sessions too, so it is the same cry-wolf.
- **What counts as a "usable" baseline**: a `files` dict and a positive numeric `at`. `head` is
  not required.
- **A matching marker with no baseline is `unverifiable`**, not `ran`. It can't change any verdict
  (no baseline already means `UNKNOWN`), but the old row made a claim the tool couldn't back.
- **The printer hides the `attribution UNAVAILABLE` line and the `NO_BASELINE_REASON` line when the
  NOTE has printed.** That is "says so once". Both remain in the receipt JSON.
- **The `--check` run used a scratch `CLAUDE_CONFIG_DIR`** instead of the real state dir. The
  reason is in section 2.

## 4. What I chose not to do

- **No lazy baseline stamp inside `--record`, and no `NOT DUE` for no baseline.** Both are
  rejected in the entry. `_nothing_to_wrap` still refuses without a usable baseline.
- **Didn't touch `archive_guard.py`.** Its decisions are unchanged, and section 4 still passes.
  Its module docstring (lines 40 to 43) still justifies skipping baseline-less roots with *"with no
  baseline, a stale `.last_wrap` ... reads `OPEN`"*. That is no longer true of `verdict()`. The
  skip is still correct (it also avoids the git work), but the sentence is stale. It's not my file.
  Proposed replacement below.
- **Didn't change 9g** (baseline present, reflog removed, pulled-and-idle -> `OPEN` from the stale
  marker). There the baseline shows that HEAD moved during this session, so "owed" is partly
  measured. It's a different blind spot from B10, and arguably B122 territory. Whether it should
  also be `UNKNOWN` is a separate question and not in B10's scope.
- **Didn't fix B11** (baseline keyed only by session id doesn't survive crash-and-resume). That is
  the *prevention* for the case this fix makes honest. It's a separate item.
- **Docs I didn't edit** now overstate the ordering guarantee. Each says, in some form, that "a

## Does this fix reintroduce its own bug one level up?

**Can any no-baseline path now read `SET`?** No, and it's now structurally impossible rather than
incidentally so:

- `verdict()` returns `UNKNOWN` before it looks at `step_states` whenever `_usable(base)` is None.
- Test 12g forges every REQUIRED step as `ran` with base `None`, `{}`, a hollow dict, and a dict
  without `at`. All four read `UNKNOWN`.
- `NOT DUE` is also unreachable, since that branch comes after the no-baseline return.
- The fix **closed** one no-baseline -> `SET` path that existed at HEAD: the hollow baseline,
  scenario D.

**Other directions checked:**

- **`UNKNOWN` as a soft landing.** This is real, bounded, and stated in section 3. It applies only
  with no usable baseline. With a baseline, every measured negative still produces `OPEN`: tests
  3a, 4, 11c and 12f pin this, including an idle session's `[SKIP] byte-identical`.
- **One value, two states.** "No baseline" vs "baseline without a snapshot" are now the same state
  on purpose (both unusable). "Key missing from the snapshot" vs "file absent at session start"
  were one state and are now split. The NOTE's cause text now covers all three ways to have no
  baseline instead of asserting one.
- **Silent loosening of the guard.** None: the guard skipped baseline-less roots before and still
  does. For a hollow baseline file, the guard used to judge the root with `verdict()` and could
  deny. It now gets `UNKNOWN` and allows with its one-line note. That matches D36's "judged only
  where this session has a baseline", since a hollow file is not one.
