### Explicit answer: can the fallback's number be mistaken for an exact count anywhere it prints?

**No.** Every call site that renders a token count in `measure_context.py`'s output goes through
`fmt_tokens(n)`, which prepends `~` whenever `TOKENS_ARE_ESTIMATED` is true and renders plain
otherwise — confirmed by grepping for every other place an integer token count could reach a
format string (`grep -n '{t\b\|{tt\b\|{n:' plugins/cairn/tools/measure_context.py`): the per-row
table cells (`fmt_tokens(t)`), the `TOTAL` row (`fmt_tokens(tt)`), the "on disk, NOT auto-loaded"
section, and both MCP-server token figures (deferred names and full schemas) all call
`fmt_tokens(...)`. The single bare `{n:,}` in the file is inside `fmt_tokens` itself — the one
place holding the raw int is also the one place responsible for labelling it, and nothing
downstream of it re-touches the number unlabelled. `bytes` columns need no marker since they are
always an exact `len(...encode('utf-8'))`, never estimated, regardless of tiktoken.
