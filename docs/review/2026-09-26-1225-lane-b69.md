Backlog item **B69: scheduled batch tasks start in Manual; make an unattended run safe without a
mode.** Model Opus 5, effort high, AFK. Worktree branch, committed locally, not pushed.

## Revision 2 (same day): push and sync rules moved from `deny` to `ask`

The user chose the `ask` proposal from section 3.1 below. So every `git push` rule and every
`sync_backlog` rule, for both the Bash and PowerShell tools, moved from `permissions.deny` to
`permissions.ask`. That is 72 rules. `deny` keeps 48: `gh pr merge`, the `gh repo` and `gh api`
writes, and `git reset --hard origin…`. The `afk/` allow is unchanged.

What the change does:
- **Unattended local runs** stall on the prompt, in `Manual` and in `Auto` alike (the docs say an
  explicit ask still prompts in Auto). They cannot push `main` or run the sync.
- **Attended sessions** get one approval card. `/cairn:wrap`'s push and sync work again in this
  repo.
- **Cloud routines are UNVERIFIED.** The permissions docs say nothing about how a routine treats
  `ask` or `deny`. The routines page (code.claude.com/docs/en/routines, read again this session)
  says a routine runs *"without stopping for approval"*, which could mean an ask is simply
  approved. `running-a-batch.md` now says: the cloud dry run attempts
  `git push --dry-run origin main`, and if that is not blocked, the rules go back to `deny` before
  the first real firing.

**New finding: the ask rules are load-bearing, not a second layer.** The brief asked for a test
that "no allow rule may match them". That cannot hold for every form, because `*` spans spaces and
colons:
- the `afk/` allow necessarily matches the six forms that start with `git push origin afk/` and
  then name `main`, such as `git push origin afk/x:main`;
- the `tools/*` and `run.sh` allows necessarily match `python plugins/cairn/tools/sync_backlog.py`
  and `sh plugins/cairn/hooks/run.sh tools/sync_backlog.py`.

For those forms only the ask rule, checked before allow, stops the push. The test pins this:
- every other main-reaching form must match no allow rule;
- the shadowed forms must match an allow and still resolve to `ask`;
- the shadowed set must be exactly those six push forms.

It follows that if a cloud routine auto-approves an `ask`, reverting to `deny` is what protects
those forms. A deny is checked before allow in the same way.

**Correction to section 5, follow-up 1.** I wrote that a GitHub ruleset on `main` "fully
separates cloud routines, which push as the Claude GitHub app". **That is wrong.** Per the routines
page, section "Repositories and branch permissions", and its line that commits and PRs "carry your
GitHub user", a routine pushes as the user's own GitHub identity. So a ruleset on `main` cannot
tell a routine from the user. It binds both, or neither if the user is on its bypass list.

What the page does say: a routine's `claude/`-prefixed branches are always accepted. A push to any
other branch is checked first and rejected if that branch is protected on GitHub, has someone
else's open PR, or carries commits by someone else. That affects `afk/`:
- a fresh `afk/` branch passes all three checks;
- whether marking `main` protected makes a routine's own pre-push check reject pushes to it is
  plausible from that wording, but UNVERIFIED.

**Why a settings file.** A scheduled task starts in `Manual` and no tool can raise its mode. Per
code.claude.com/docs/en/permissions (read this session), `permissions.allow` rules apply in every
mode, and deny is checked before ask and allow in every mode. An allow can never carve an exception
out of a deny. Local scheduled tasks and cloud routines both read the committed file, so it is the
one mechanism.

**What the docs say about matching**, and what these rules rely on:
- `*` matches any text, spaces included. A rule with no `*` is an exact match.
- A trailing ` *` also matches the bare command, but only when it is the rule's only wildcard.
- `:*` **at the end** of a specifier is the same as a trailing ` *`.
- Compound commands (`&&`, `||`, `;`, `|`, `&`, newline) are split. Each subcommand must match an
  allow rule, and a deny applies if any subcommand matches, including nested subshells and
  `$(...)`.
- Wrappers `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin` and bare `xargs` are
  stripped before matching. A deny matches past any leading `VAR=value`. An allow matches past only
  a known-safe one.
- A rule "matches the command text Claude writes". `git -C . push`, `git 'push'` and `sh -c '…'`
  are the docs' own examples of forms `Bash(git push *)` does not stop.
- Allow rules with a `*` before the subcommand get a startup warning. Deny rules may put `*`
  anywhere.
- `permissions.allow` from a project `.claude/settings.json` applies only once the folder's
  workspace trust has been accepted. A `claude -p` or SDK run never shows the dialog, so allow rules
  stay off there unless `hasTrustDialogAccepted` is set by hand. Deny and ask rules are not gated.
- Protected paths (`.git`, `.claude` except `.claude/worktrees`, and others) are never pre-approved
  by allow rules. In `Manual` a write there prompts.
- In `auto` mode the classifier by default **allows pushes to any branch, the default branch
  included**. So in Auto, deny rules are the only guard on `main`.
- `defaultMode: auto` and `bypassPermissions` in a project settings file are ignored.

**Allow-list shape.** The push allow is exactly `Bash(git push origin afk/*)`. No `-u`, because
the `*` spans spaces: any allow that admits a flag admits `--all`, `--mirror` and `--force` too.
`gh pr create --head afk/…` does not need an upstream. The deny list then removes everything the
trailing `*` would otherwise let through: a second refspec (`*afk/* *`, plus a tab variant), a
colon (`*:main`, `*:`, `*: *`, `*://*`), a flag anywhere (`-*`, `* -*`), `+`, `HEAD`, `@`,
`heads/`, quotes, backslash, `$`, backtick, `{`, `[`, `?`. With those, what an allowed push can
still say is `git push origin afk/<one token with none of those characters>`.

**The `:*` trap, caught by the test.** My first draft had `Bash(git push *:*)`, meaning "a push
containing a colon". Under the documented rule that `:*` at the end is a trailing wildcard, it
reads as `git push * *`. That denies the legitimate `git push origin afk/…` too, so every
unattended PR would have failed. The emulation flagged it (test 3 failed). It is replaced by
colon rules that do not end in `:*`, and test 9 now forbids any rule ending in `:*)`.

## 3. Decided on your behalf

1. **[Resolved in Revision 2: the user chose `ask`.]** Original text kept for the record.
   **The deny list also binds ATTENDED sessions in this repo.** A project
   settings deny cannot tell a scheduled firing from you sitting there. Once this merges:
   - `/cairn:wrap` step 5's push to `main` is denied in this repo, whatever form it takes.
   - A `HITL` item's push to `main` is denied too, although `rules/CLAUDE.md` says a HITL item
     pushes.
   - Step 8a's `sh "<root>/hooks/run.sh" tools/sync_backlog.py` is denied (the `sh *sync_backlog*`
     rule).

   I built what was decided (`main` stays push-denied; sync denied) and did not reopen it. But the
   brief said sync is denied *unattended*, and a project file cannot express "unattended". The
   alternative is to move just the main-reaching push rules and the sync rules from `deny` to
   `ask`:
   - Unattended in `Manual`: an ask prompts, the run stalls, nothing goes out.
   - In `Auto`: the docs say explicit ask rules still force a prompt, so it still stalls.
   - Attended: you get one approval card.

   The cost is that a mistaken main push in an unattended run stalls the run instead of failing
   fast. Filed as a proposed decision below. Until it is answered, you push `main` yourself from
   your own terminal. I have not checked whether Claude Code's `!` shell prefix is subject to
   permission rules.
2. **The push allow has no `-u`/`--set-upstream`.** Flags cannot be allowed safely when `*` spans
   spaces (see section 1). The doc tells the run to push as `git push origin afk/<branch>` and pass
   `--head` to `gh pr create`.
3. **`gh api` is denied by write flag, not wholesale:** `-X`, `--method`, `-f`, `-F`, `--field`,
   `--raw-field` and `--input` are denied, so attended reads still work. Denied `gh repo`
   subcommands: create, delete, edit, rename, archive, unarchive, sync, fork, set-default and
   deploy-key.
4. **PowerShell rules mirror the push, sync, gh and reset denies**, because Windows sessions have
   both tools. There are no PowerShell allows, so a batch that reaches for PowerShell prompts
   (stalls) rather than running unguarded. On a machine with no PowerShell tool, such as a cloud
   routine on Linux, these rules may produce an unknown-tool startup warning. The docs exempt only
   names containing `_` or `*`, and I have not confirmed the behaviour.
5. **Two `.gitignore` lines.** `.claude/worktrees/` was ignored only through this clone's
   `.git/info/exclude`, which a fresh clone (a cloud routine) does not have. `.claude/settings.local.json`

6. **Some broad allows were kept because the brief listed them.** `git branch *` admits
   `branch -D`, `git worktree *` admits `worktree remove --force`, and `git switch *` admits
   `switch -C`. All three are local, and none reaches `origin`.
7. **Legitimate commands the deny list also refuses.** `git -C <dir> commit -m "…push…"` and
   `git -C <dir> log --grep=push` match `git -* push*`. `sh -c`/`bash -c` with "push" anywhere in
   them are refused too. A refusal fails fast, it does not stall, and dropping `-C` avoids it.
8. **A rule that the docs do not confirm:** the tab-separated second refspec is written as a
   literal tab (`"Bash(git push *afk/*\t*)"`). The docs do not say whether the matcher normalises
   whitespace.

## 5. Which main-reaching push forms can still get past the deny list?

*(Revision 2: these rules are now `ask`, not `deny`. The patterns are the same, so the analysis
below is unchanged for local runs, where an ask stalls exactly where a deny would refuse. In a
cloud routine it holds only if the routine honours `ask`, which is UNVERIFIED. See the top of this
file.)*

**In `Manual` (the mode a scheduled task actually starts in): one real class.** Every form below
except (d) matches no allow rule, so it prompts and the run stalls. Nothing reaches `main`.

- **(d) Code the run wrote, executed by an allowed interpreter.** `Write` is allowed, and so are
  `python plugins/cairn/tools/*` and `sh plugins/cairn/hooks/run.sh *`. So
  `python plugins/cairn/tools/x.py`, where `x.py` calls `subprocess.run(["git","push","origin","main"])`,
  is allowed. `run_tests.py` running a new `test_*.py` is the same case, and so is `..` traversal
  in the allowed path. **No command-text rule and no PreToolUse hook can close this**, because the
  command text is innocent.

**In `Auto` (if someone sets it)**, the classifier decides all of the following, and by default it
allows pushes to any branch, including the default one:

- **(a) Quoting or escaping the verb or program:** `git 'push' origin main`, `"git" push …`,
  `g\it push …`.
- **(b) A git alias that already exists** in user or system config (`git p origin main`). The run
  cannot create one: `git config` is not allowed.
- **(c) Wrappers that are neither stripped nor denied:** `exec git push …`, `xargs -n1 …`,
  `find … -exec`, or a script file run with `sh script.sh`.
- **(e) Config injected through the environment:**
  `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=remote.origin.push GIT_CONFIG_VALUE_0=refs/heads/afk/x:refs/heads/main git push origin afk/x`.
  The deny matches past the assignment and sees a clean afk push. In `Manual` the allow does not
  match past an unknown assignment, so it prompts.
- **(f) An unquoted glob refspec** such as `ma*`, if the working directory holds a matching file.
  A literal `*` cannot be written in a rule. Git may reject such a refspec anyway (unverified).
- **(g) Whitespace the matcher might normalise differently** (tab, CR). The tab has a rule, but
  the docs do not confirm how it matches.

**Proposed follow-ups (for a separate item, not this lane):**

1. **Branch protection on `origin`'s `main`.** ~~It fully separates cloud routines, which push as
   the Claude GitHub app~~ **Wrong. See Revision 2:** routines push as the user's own GitHub
   identity, so a ruleset cannot tell a routine from the user. It still ignores how the command is
   spelled. A routine's own pre-push check may also refuse a protected branch (unverified).
2. **A project PreToolUse hook `push_guard.py`** (a `.claude/settings.json` hook, not a plugin
   hook, since it is repo-specific). It would shlex-split each Bash/PowerShell subcommand, strip
   wrappers and env, and find a git invocation by any path. It would skip git's global options,
   resolve aliases with `git config --get alias.<x>`, and on `push` run
   `git push --dry-run --porcelain <same args>`, denying if any destination is `refs/heads/main`
   or any `GIT_CONFIG_*` is set. That closes (a), (b), (c), (e), (f) and (g) for the Bash tool.
   It cannot close (d).
3. **A local `pre-push` git hook** that refuses `refs/heads/main`. It sees the real refs whatever
   the command, (d) included, but it binds your own pushes too, and `--no-verify` from a
   subprocess skips it. So it only helps if paired with a marker that unattended runs carry and
   you do not. No such marker exists today.
