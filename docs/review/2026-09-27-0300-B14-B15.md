## What changed and why

**B14 — `fence_check.py` no longer checks nothing when called with no arguments.** The old
`for path in sys.argv[1:]` had no default, so a bare run read zero files and printed
`fence check: 0 line(s)...` / exit 0 — byte-identical to a real clean pass. `main()` now falls
back to a default set — `NEXT.md`, `BACKLOG.md`, `CHANGELOG.md`, `INBOX.md` — filtered to
whichever of the four actually exist in the current directory, and always prints which ones it
used and how many it read (`across N file(s) read`), so a run over an empty directory reads
*"none of ... is present"* / `across 0 file(s) read` rather than a silent pass. Passing paths
explicitly is unchanged: every pattern still applies to every path given, exactly as before B14.

The default set deliberately excludes the public docs (`README.md`, `docs/guide.md`,
`docs/file-formats.md`): those documents fence deliberate *examples* of the same syntax
(`## B12.`, `**W3.`, an INBOX bullet) that no line-start parser in this plugin ever reads.
Measured directly (see Verification): scanning those three by default would report 9 hits, all
of them format documentation, not a real hazard — so they stay explicit-args-only.

**B15 — a bullet is only "structure" inside INBOX.md, and only outside a fence.** Both bullet
counters (`wrap_receipt._inbox_bullets()`, `session_orientation._inbox_items()`) matched
`- `/`* ` at line-start with zero fence awareness — the live incident was an INBOX.md intake
contract whose four *example* bullets, quoted inside a fenced code block, were counted as 5
un-triaged items instead of the 1 real one.

Fix, in the preferred order the brief named: (2) both counters now exclude fenced lines before
counting, via a new shared module, `plugins/cairn/hooks/fence_scan.py` — one `FENCE_RE` (``` and
~~~, same as `backlog_file._strip_fences()`), one `BULLET_RE` (now requires actual content after
the marker, so a bare `- ` line is not an item), and a `mask()`/`strip_bullets_in_fences()` pair
both counters and `fence_check.py` call. `fence_check.py` also grew the (1) half — a bullet
pattern — but scoped to files literally named `INBOX.md` only: a bullet fenced inside a
BACKLOG.md or CHANGELOG.md body is prose (an example list in an item's own writeup), not
structure any parser in this plugin keys off, and applying it everywhere would cry wolf on every
such body. That scoping is a decision, argued below.

**Unclosed fence — asymmetric on purpose, not a shared default.** `backlog_file._strip_fences()`
treats an unclosed fence as fenced-to-EOF, silently — correct for BACKLOG/CHANGELOG parsing,
where the risk is a false positive (pasted output read as a real item). For an INBOX.md bullet
*count*, the risk runs the other way: silently blanking everything after a forgotten closing
``` would make every real trailing bullet vanish from the un-triaged count with no signal at
all — B15's own bug, recurring one level up in the fix meant to close it. So `fence_scan.mask()`
only *measures* whether a fence closed and hands the fact back; it never decides for the caller:
- `wrap_receipt.py`'s `inbox` step now **never certifies `ran`** past an unclosed fence, even
  when the visible (partial) count is 0 — it forces `skipped` with a reason naming the unclosed
  fence, rather than the `_bullets == 0` count deciding the state.
- `session_orientation.py` prints an explicit `WARNING: INBOX.md has an unclosed fence...` line
  alongside whatever count it did manage, rather than silently under-reporting.
- `fence_check.py` keeps its original behaviour unchanged: it still flags bullets/headings found
  *inside* an unclosed fence as hits (that content would still be misread as structure by a
  naive parser) and still prints its existing `WARNING unclosed fence` note. That is a
  deliberately different choice from the two counters, because `fence_check.py`'s job is "report
  a hazard", not "produce a trustworthy drained-count" — see the dedicated question below.

## Decided on Sheldon's behalf

- **The bullet pattern in `fence_check.py` is scoped to files named exactly `INBOX.md`, in BOTH
  default and explicit-argument modes.** The brief's "with arguments, keep today's behaviour"
  is read as applying to *which files get scanned* (unchanged: explicit args are used verbatim),
  not to whether a brand-new pattern applies indiscriminately. Applying the bullet rule to every
  explicit path too (including a BACKLOG.md-shaped fence full of example bullets) would
  reintroduce exactly the cry-wolf B15 is against, just via the explicit-path door instead of the
  default one. Tested directly (`test_fence_check.py` 2b/2c): a fenced bullet list in a
  BACKLOG.md body, and the same shape under an arbitrary filename, both read clean.
- **`fence_check.py`'s own handling of an unclosed fence is intentionally NOT the same choice as
  the two counters' (see "does this reintroduce its own bug" below).** It keeps reporting hits
  inside an unclosed fence (unchanged from before this lane) rather than adopting the counters'
  "unmeasurable, don't count it" stance, because its job is orthogonal: flag content a naive
  parser would misread, not certify a drained inbox.
- **An unclosed fence forces `wrap_receipt.py`'s `inbox` step to `skipped`, never `ran`,
  regardless of the (partial) count.** The alternative — trust the partial count when it happens
  to be 0 — was rejected because it can misreport a genuinely un-triaged INBOX.md as `ran`
  whenever the fence break happens to land before any real bullet, which is indistinguishable
  from "empty" without a warning next to it. `skipped` plus a reason naming the unclosed fence
  keeps `REQUIRED` behaving normally (verdict logic that already treats `skipped` as "not ran"
  needed zero changes) while being honest about *why*.
- **`BULLET_RE` now requires content after the marker** (`^\s*[-*]\s+\S`), tightening
  `session_orientation.py`'s previous bare `.startswith(("- ", "* "))`. A `- ` line with nothing
  after it is formatting, not an un-triaged item; `wrap_receipt.py` already had this stricter
  shape, so unifying picked the stricter of the two rather than the looser one.
- **The shared fence-tracking module (`fence_scan.py`) is a new sibling of
  `backlog_file._strip_fences()`, not a rewire onto it.** `backlog_file.py` belongs to another
  lane; importing its leading-underscore internal would couple two lanes' releases, and this
  module's callers need the unclosed-fence fact reported back, which `_strip_fences()` does not
  do (by design, for its own callers). Duplication is small (about a dozen lines) and documented
  as deliberate in the new file's own docstring.
- **`fence_check.py`'s "no default file present" case still exits 0** (e.g. an empty directory).
  This is not a vacuous pass in the B14 sense: the printed line says explicitly that nothing was
  present and nothing was read (`across 0 file(s) read`), so it cannot be mistaken for "checked
  and clean" the way the old silent zero-files case could.

### Does this reintroduce its own bug one level up?

Asked directly, per the brief: **can an unclosed fence make either counter silently under-report
a real un-triaged item with no signal?** No — `mask()`/`strip_bullets_in_fences()` always report
`unclosed_at` back, and both call sites are required to act on it (tested:
`test_wrap_receipt.py` 13's unclosed-fence case forces `skipped`, never `ran`;
`test_session_orientation.py` section 4 asserts the swallowed bullets are excluded from the
*shown* list but the fact of the unclosed fence is still returned, non-`None`, for the caller to
print). Nothing in this change lets a `None` unclosed-fence signal coexist with lines that were
actually blanked past an open marker — `mask()` returns the two together from one pass over the
same lines, so they cannot drift apart.

The one place this asymmetry could look like a bug from a distance: `fence_check.py` still
*counts* bullets inside an unclosed fence as hits (unlike the two counters, which exclude them).
That is not the same bug recurring — `fence_check.py` was never trying to produce a trustworthy
"how many real items" number; it is a hazard scanner, and content behind an unclosed fence is
still a hazard a naive parser could misread. Making it match the counters' behaviour (stop
counting past an unclosed fence) would be the actual regression, silently hiding real B85/B15-shaped
hits behind a broken fence marker. Both choices are stated explicitly in this lane's owned code
and tests, not left implicit.
