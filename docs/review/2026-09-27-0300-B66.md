## What changed and why

**1. `plugins/cairn/hooks/version_drift.py` — `_rules_drift` gained a NEWER-rules branch.**

Since v1.63.0 (D33), `install_rules` **keeps** a rules block that is newer than the plugin
(B63's downgrade refusal) instead of rolling it back. But `_rules_drift`'s only non-silent,
non-"missing", non-"no-marker" branch said, unconditionally:

> "this session is running NEW code against OLD rules. Restart to let `install_rules` resync"

That is backwards when the *rules* are the newer side: the plugin is the old side, and a restart
will not resync anything (`install_rules` will just keep refusing, forever, until the plugin
itself is updated). `tools/check_install.py` already had the correct STALE branch for this
direction (its `compare_versions(rules, installed) == 1` case, lines 369–377), so I added the same
branch to `_rules_drift`, worded to match it:

```python
if compare_versions(rules_version, installed_version) == 1:
    # B66: the rules block is NEWER than the installed plugin. Since v1.63.0 (D33) `install_rules`
    # KEEPS a newer block rather than roll it back, so the generic wording below -- "restart to
    # resync" -- is backwards in this direction: the PLUGIN is the old side, and restarting will
    # not touch it. Worded like `check_install.py`'s matching STALE branch.
    return (f"⚠ {where}'s rules block is v{rules_version}, NEWER than the installed cairn "
            f"plugin v{installed_version}. `install_rules` keeps a newer block rather than roll "
            f"it back (B63), so a restart will NOT resync this — the plugin is the old side. "
            f"Update it: `claude plugin marketplace update superbole`, then `claude plugin "
            f"update cairn@superbole`, restart.")
```

Placed after the `missing`/`no-marker` checks (which must still return first — they have no
parseable `rules_version` to compare) and before the old unconditional branch, which now only
fires when the rules are the *older* side (unchanged behaviour) **or** when `compare_versions`
returns `None` (unparseable input — no direction evidence, see "asked of the fix" below).

**2. `plugins/cairn/hooks/install_rules.py` — the B63 refusal now names both commands.**

The refusal in `_install_block()` (the "NEWER installed block, OLDER plugin" branch) told the user
to run only `claude plugin update cairn@superbole`. `check_install.py`'s matching remedy (already
correct) runs `claude plugin marketplace update superbole` **first**, then `claude plugin update
cairn@superbole` — because a stale local marketplace cache can otherwise answer "already at the
latest version" and the single-command remedy silently fails. Changed the refusal to name both,
in that order, and noted why:

```python
"the newer block was kept. This session is running an OLDER copy of the "
"plugin; tell the user to run `claude plugin marketplace update "
"superbole`, then `claude plugin update cairn@superbole`, restart. (A "
"stale marketplace cache can otherwise answer \"already latest\" — see "
"`tools/check_install.py`'s matching remedy.)"
```

`test_install_rules.py`'s test 14 assertion (`"claude plugin update cairn@superbole" in report`)
is a substring check and still passes unchanged — confirmed by the run below.

**3. `check_install.py` — not touched.** It already said the right thing in both places; it was
the reference wording, not a defect. No edit needed.

**4. `plugins/cairn/tools/test_version_drift.py` — updated one assertion, added a new test block.**

- The existing "real hook: warns when they diverge" case stages `installed_plugins.json` at
  `0.0.1` against a CLAUDE.md block also at `0.0.1`, then runs `session_orientation.py` for real.
  That hook calls `install_rules.install()` **first**, which — since the staged block (`0.0.1`) is
  older than the live plugin version — performs an ordinary upgrade and rewrites the staged
  CLAUDE.md block to the **live** version. By the time `version_drift.check()` looks, the staged
  `installed_plugins.json` is still `0.0.1` but the rules block is now `live` — i.e. the rules are
  now the *newer* side. So this case now exercises the NEW branch, not the old "OLD rules" one.
  Updated the assertion from `contains(..., "OLD rules")` to `contains(..., "NEWER than the
  installed")`, with a comment explaining why.
- Added a new block of unit tests directly against `_rules_drift()` (no subprocess) covering:
  - rules newer than installed → both versions named, "NEWER than the installed", "will NOT
    resync", both remedy commands present, and explicitly **not** the old "OLD rules" wording.
  - an installed-version string that does not parse (`"weird-1.2.3"`) must **not** be misrouted
    into the NEWER branch on a guess — it must fall through to the old, direction-agnostic
    wording. (`rules_version` itself can never be unparseable here: `_MARKER_RE` only ever
    captures `[0-9.]+`, so the untestable half of "which side is unparseable" is the installed
    side, which is what I exercised.)
  - equal versions still return `None` (silent), unaffected by the new branch.

## Decided on Sheldon's behalf

1. **Did not touch `check_install.py`.** The brief said to edit it "only if strictly needed to
   make the two remedies identical" — it already had the correct wording in both places (the
   NEWER-rules STALE branch, and the two-command marketplace-then-plugin-update remedy), so
   `version_drift.py` and `install_rules.py` were brought to match it rather than the reverse.
2. **Where the unparseable-version test lives.** `_MARKER_RE` in `version_drift.py` only ever
   captures `[0-9][0-9.]*`, so a rules-block version read off disk is always parseable by
   construction — there is no way to stage an unparseable `rules_version` through `rules_state()`.
   I tested the other half instead: an unparseable `installed_version` passed directly to
   `_rules_drift()` (its actual parameter, not disk-read), confirming it falls through to the
   direction-agnostic default rather than the new NEWER branch — this is the case
   `compare_versions` returning `None` actually protects against in practice.
3. **Ordering of the new branch.** Placed it after the `state == "missing"` / `state ==
   "no-marker"` checks (which have no `rules_version` to compare) and before the old default
   branch, so an unparseable-`installed_version` or unparseable-`rules_version` case (impossible
   today per point 2, but the code doesn't assume it) falls through safely to the old wording
   rather than crashing or guessing.
4. **Did not rewrite `_rules_drift`'s docstring** beyond what the diff needed — left the existing
   "Silent when there is nothing to compare against" paragraph as-is since it still accurately
   describes the `installed_version is None` early return.
