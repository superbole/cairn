## What changed and why

### B63: refuse to downgrade a newer rules block

**`plugins/cairn/hooks/version_drift.py`**
- Added `parse_version()` and `compare_versions()`. This is now the one version parser. It is strict
  on purpose: it accepts dot-separated integers only, and trailing zeros are dropped, so `1.62`
  equals `1.62.0`. Anything else parses to `None`, and every caller treats `None` as "no evidence
  of a downgrade". `compare_versions` returns -1, 0 or 1, or `None` when either side doesn't parse.
- The existing drift messages are unchanged. See "Chose not to do" for the one that is now wrong in
  one direction.

**`plugins/cairn/hooks/install_rules.py`**
- Imports `compare_versions` from `version_drift`. The import is guarded the same way as
  `ensure_profile_file`. If the import fails, a stub returns `None`, which means today's behaviour
  (write). It never fails a session.
- In `_install_block()`, the new check goes **after** the silent early return. The common path
  computes nothing new. If `compare_versions(installed, version) == 1` and the plugin version is not
  the `"0"` failure sentinel from `_plugin_version()`, it writes nothing, backs up nothing, and
  returns one `[to the agent]` line. That line names both versions, says the newer block was kept,
  and gives `claude plugin update cairn@superbole`, then restart. It returns `in_context=True`.
- New `_refusal(target, reason, consequence)`. Both the MalformedBlock refusal and the downgrade
  refusal now come from it, so they share one voice:
  `Did NOT update the cairn rules block in <target>: <reason>. The file was left untouched; <consequence>`.
  The MalformedBlock text differs by one punctuation change: ", so the rules…" became "; the
  rules…". Its substance is unchanged.
- One DESIGN RULES bullet was added to the module docstring.
- Equal-version and older-version paths are unchanged. So is an unparseable version on either side,
  as the brief asks.

**`plugins/cairn/tools/check_install.py`** (this is the one-level-up consequence of B63)
- It now imports `compare_versions`. A new STALE branch handles **rules newer than the installed
  plugin**. The old message said "start a session… install_rules resyncs the block". After B63 that
  is false in this direction, because install_rules keeps the newer block. The new message names
  the plugin as the stale side and gives the marketplace update plus plugin update. The exit code is
  still 1.

### B26: say what changed, not just `vX → vY`

**`plugins/cairn/hooks/install_rules.py`**
- On the update path only, after a successful write, the change line now carries three things:
  - A count, `Rules text: +A −R ~C lines`, from `difflib` over the two blocks with the header line
    dropped. The version is already on the line, and counting the header would make every pure bump
    report "~1 line".
  - Where the change is, `in: X, Y, Z (+N more)`: the nearest `#` heading of each changed line. At
    most 3 are named, each cut to 40 characters.
  - The exact command, `git diff --no-index -- "<backup>" "<target>"`. The backup path comes from
    the existing `_backup()` naming.

  A pure version bump says `Rules text unchanged — only the version marker moved`. A same-version
  edit reads `vX → vX (same version, different content)`, so it isn't just a confusing `vX → vX`.
- `difflib` is imported inside `_change_summary()`, so the silent path doesn't even pay for the
  import. If the summary raises, the line degrades to the pre-B26 wording and never to silence.
  Refusals and first installs never compute it.
- The line is still ONE line.
- New `block_digest(block)`: sha256 of the block text, 12 hex characters.

**`plugins/cairn/tools/check_install.py`**
- A new `block     :` line shows the digest of the installed **block**, never the file and never
  any content. It uses `install_rules._find_block`, the installer's own finder. In a checkout of

  `install_rules._block`. When the version strings match and the digests don't, it adds
  `— SAME version, DIFFERENT block`.
- It is informational only. The `OK`/`STALE`/`UNKNOWN` verdicts and the exit codes are untouched.

## Decided on Sheldon's behalf

1. **The helper went into `version_drift.py`**, with no new module. It already reads the versions,
   and `install_rules` imports it with the same guard as `ensure_profile_file`. If that import ever
   fails, the guard is off and behaviour is exactly v1.62.0's. That is silent, but it is the
   "never fail a session" rule, and the file is shipped alongside.
2. **The parser is strict.** `1.2.0-rc1` and anything else non-numeric parses to `None`, which
   means "no evidence", so the write goes ahead. The alternative, the lenient `_newer()` in
   `check_install.py` (non-digits count as 0), would let a malformed string decide a refusal.
3. **The `"0"` version is treated as unknown.** `_plugin_version()` returns `"0"` when `plugin.json`
   can't be read. Without this exception, every installed block would look "newer than v0" and the
   refusal would fire with a misleading "this plugin's v0" message.
4. **The downgrade refusal repeats every session** until the plugin is updated, just as
   MalformedBlock does. It is not rate-limited, because nothing else will fix it.
5. **B26 counts leave out the header line.** A pure bump says "Rules text unchanged — only the
   version marker moved" instead of "~1 line".
6. **Sections are named by the nearest heading at any level** (`#` to `######`), not only `##`. The
   rules file's real structure uses `###` a lot, and naming the `##` parent would be less
   informative. The cap is 3 names at 40 characters each, then `(+N more)`.
7. **The diff command is `git diff --no-index`** rather than `diff -u`. Git exists on every machine
   the plugin runs on, and plain `diff` is not on the Windows PATH outside Git Bash.
8. **The digest is its own `install_rules.block_digest()`, not `wrap_receipt._digest()`.** The brief
   said to reuse `_digest`, on the premise that "the payload imports no `hashlib` elsewhere". That
   premise is stale: `install_rules` has imported `hashlib` since B25. And `_digest(path)` hashes a
   **whole file**, which here includes the user's own notes outside the markers, so two machines
   would never match. That defeats the point of the digest.
9. **check_install's digest never affects the exit code**, including the "SAME version, DIFFERENT
   block" flag. The brief requires the exit semantics to stay unchanged.
10. **The reversed-direction STALE message in check_install** was added as B63's consequence (see
    "What changed").

**Proposed `docs/decisions.md` rows:**

> **B63: the installer refuses to write a rules block older than the one installed.** When both the
> installed marker version and the plugin version parse (dot-separated integers only) and the
> installed one is newer, `install_rules` writes nothing, backs up nothing, and says so every session
> in the same refusal voice as MalformedBlock. An unparseable version on either side, or the
> `"0"` sentinel from an unreadable `plugin.json`, is not evidence and falls through to the write.
> *Rejected: newest content wins, decided by diffing the bodies.* A body can't say which of two
> versions is newer; the marker can. Diffing would also pick arbitrarily between two machines'
> edits. *Rejected: one rules block per process.* That is impossible, because `~/.claude/CLAUDE.md`
> is one file. *Rejected: a lenient parser* (non-digits read as 0). It would let a malformed version
> string decide whether the rules get written. Cost of the decision: an older installer that still
> runs leaves its session without its own rules text. That is accepted, because it is the older
> text.

> **B26: the rules-block change line carries a count, the touched headings and the exact diff
> command. The block digest in `check_install` is its own function.** *Rejected: a semantic
> classifier* of what changed (D9: do not invent one). The headings are a location, not a meaning,
> and the diff command is the evidence. *Rejected: reusing `wrap_receipt._digest()`.* It hashes a
> whole file, including the user's own text outside the markers, so no two machines would ever
> match. Its premise (no `hashlib` in the payload) has been false since B25. *Rejected: counting the
> header line.* Every pure version bump would read "~1 line changed".

## Chose not to do

- **`version_drift._rules_drift` is left alone, even though B63 makes one direction of its message
  wrong.** When the rules block is newer than `installed_plugins.json`, it still says "this session
  is running NEW code against OLD rules. Restart to let `install_rules` resync". After B63, neither
  half is true: the code is the old side, and a restart won't resync. Fixing it needs a matching
  change in `plugins/cairn/tools/test_version_drift.py`. Its "real hook: warns when they diverge"
  case stages installed `0.0.1` against the live rules and asserts `"OLD rules"`. That file is
  outside this lane's ownership, so the fix is left to the orchestrator: add a
  `compare_versions(rules_version, installed_version) == 1` branch in `_rules_drift` worded like
  check_install's new STALE branch, and update that one assertion. **This should be recorded as a
  backlog item. It is not a blocker.**
- **`check_install._newer()`, the lenient parser, is not migrated onto `compare_versions`.** It only
  picks between two advisory notes when `repo != installed`, where leniency is harmless. Migrating
  it would change the output for non-numeric versions, with no test asking for that.
- **B26 adds no summary on the first-install, prepend or refusal paths.** On first install and
  prepend there is no outgoing block to compare against, and the refusal prints its own line (the
  brief says not to add one there).
- **No version bump, CHANGELOG, `README.md` check or decisions row.** The orchestrator does those.
  For the README check the brief asks for: this lane changed no `rules/CLAUDE.md` or `SKILL.md`
  text, so neither the README rule nor the `incidents.md` rule is triggered by this lane's diff.
  Other lanes' rules edits may trigger them.
- **The cost was not re-measured with tiktoken.** It isn't installed (B23), so the figures above
  are labelled `~` estimates.
- **The provenance of the v1.62.0 process on NB1 was not chased**, as the brief says.
